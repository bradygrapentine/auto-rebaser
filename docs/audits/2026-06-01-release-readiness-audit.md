# Release-Readiness Audit — 2026-06-01

**Verdict: ship-with-followups (one true must-fix should land first).** The CT-wave (CT-2/3/4) and the v2 multi-account settings split are broadly solid, but two distinct root causes produce real, user-visible wrong behavior. (1) A **cross-account scope leak** in the freshly-shipped CT-4 notification path: `notify()` reads/writes its throttle via the deprecated implicit-id wrappers instead of the threaded `AccountScope`, so account A's throttle suppresses/clobbers account B's notifications. (2) A **settings-partition drift** for `enableIgnoredRepos`: it is declared global in four places but never actually persisted/read as a global on the v2 path, so turning it OFF silently reverts to ON, re-activating the user's ignored-repos list against intent — and the v1→v2 migration loses the v1 value on the next save. Both are correctness bugs in load-bearing paths and should be fixed before the next store push; everything else is should-fix hardening, test-gap closure, or accessibility polish. After verification, two reviewer escalations were downgraded (the CT-2 fail-open and the migration partition-drift entry, which is the same root cause as the store finding and is merged below).

---

## Must-fix

- **[engine-correctness] CT-4 notification throttle is read/written under the active account, not the polling account — cross-account scope leak** (`src/background/notifications.ts:127,168`; called from `src/background/poll-cycle.ts:1147,1155`) — `notify()` takes no `accountId`/`AccountScope` and uses `readAccountKey('notif_throttle')`/`writeAccountKey`, which `multi-account.ts:351,414` document as `@deprecated for SW-side use` because they resolve the namespace via `getActiveAccountId()`/override, NOT the explicit scope. `runPollCycle` iterates every signed-in account with its own `scope` (poll-cycle.ts:120-132) and dispatches notifications from inside `runAutomationsPass` (poll-cycle.ts:924-cycle, notify at 1147/1155). Result: account B's notifications are suppressed by account A's throttle entries, and B's throttle write clobbers A's map. This is exactly the SW-eviction/override-desync failure the rest of the cycle was refactored to avoid by threading `AccountScope` (which already wraps `loadStoreFor`/`getPingedStoreFor`/`getRerequestStoreFor`). CT-4 shipped this cycle, so the notify path is freshly load-bearing. _Fix:_ thread `AccountScope`/`accountId` into `notify()` and route the throttle read/write through `readAccountKeyFor(id,'notif_throttle')`/`writeAccountKeyFor`, mirroring every other per-account access in the cycle; pass `scope` from `runAutomationsPass` into both `notify()` calls. Add a cross-account notify test (account A throttled must not suppress account B).

- **[architecture] `enableIgnoredRepos` is declared global but never persisted/read as a global — v2 save silently reverts the toggle, and v1→v2 migration loses it** (`src/core/automations-store.ts:31,115-116,120,70-77,141-151`; `src/core/storage/migration.ts:148-151`) — Merged from two reviewers (store + migration lenses; same root cause). `GLOBAL_KEYS` lists `enableIgnoredRepos` (line 31), so `isGlobalKey` EXCLUDES it from the per-account write (line 120), but the v2 global-write block only sets `ignoredRepos` + `enableKeyboardShortcuts` (lines 115-116) — `enableIgnoredRepos` is written nowhere. Symmetrically `getAutomationSettings` (70-77) and `getAutomationSettingsFor` (141-151) only re-read those two globals. Net: a user who turns OFF "enable ignored repos" has it dropped from the per-account write and never stored, so the next read falls back to `DEFAULT_AUTOMATION_SETTINGS.enableIgnoredRepos = true` — the toggle reverts to ON and the ignored-repos list re-activates against intent. `poll-cycle.ts:151` and `PRListView.tsx:82` both gate on this field, so the ignore feature behaves opposite to the saved setting. The migration mirror-bug: `stripGlobalKeys` (migration.ts:149) only destructures out `ignoredRepos`/`enableKeyboardShortcuts`, and the global-write block (98-111) omits `enableIgnoredRepos`, so a migrated user who disabled it in v1 keeps it once but loses it on their next save. Root cause is the same partition declared in four unsynchronized places. _Fix:_ derive the partition from ONE exported tuple (e.g. `GLOBAL_AUTOMATION_KEYS`) and build `GlobalSettings`, `PerAccountSettings`-Omit, `isGlobalKey`, AND migration's `stripGlobalKeys` + global-promotion loop from it; then `setGlobalSetting('enableIgnoredRepos', …)` + re-read in both getters (or drop it from `GLOBAL_KEYS` and let it ride per-account). Add a v2-path roundtrip test asserting `enableIgnoredRepos=false` survives save→read with an active account.

## Should-fix

- **[engine-correctness] Notification throttle key is not repo-qualified — same PR number in two repos shares one throttle slot** (`src/background/notifications.ts:80-82`) — `throttleKey(prNumber, event)` returns `${prNumber}:${event}` with no repo component; PR #42 in repoA and #42 in repoB collide, so a rebase notification for one suppresses the other for up to 1h. The activity-log dedup keys on `${repo}#${number}` (poll-cycle.ts:1104), so the convention exists. _Fix:_ include repo in the key (`${repo}#${prNumber}:${event}`); `NotifPayload.repo` is already available. (Co-located with the must-fix scope leak — fix both in the same `notify()` pass.)

- **[security] CT-4 notification click opens an unvalidated API-supplied URL via `chrome.tabs.create`** (`src/background/notifications.ts:204-216,188-197`) — `handleNotificationClick` reads a stored URL and calls `chrome.tabs.create({url})` with no scheme/origin check. On `github.com` GitHub controls `html_url` so it is safe, but for a configured `enterpriseHost` (GHES) the URL is whatever that server returns — a malicious/compromised GHES the user pointed at could return `https://evil.example/…` (or a `data:` URL) and have the extension open it on click. This is the SEC-2/SEC-6 trust-boundary class the OWASP review hardened for the auth path but which is not enforced on this new CT-4 sink; `assertGithubOrigin` already expresses the allowlist. Downgraded from a borderline must-fix because the dominant (github.com) deployment is safe and exploitation requires a hostile enterprise host. _Fix:_ validate at `persistClickTarget` time (so a bad URL never lands in storage): `new URL()`, require `https:`, assert hostname is `github.com` or the configured `enterpriseHost` (reuse `assertGithubOrigin`); no-op otherwise.

- **[engine-correctness] Reviewer-phase re-arms auto-merge when `getPR` returns no `head.sha`** (`src/background/poll-cycle.ts:739-741,791,799-802`) — `headChanged = cached?.lastSeenHeadSha != null && cached.lastSeenHeadSha !== headSha`; when `pr.head?.sha` is undefined (degraded detail, fork edges), the inequality is true for any armed PR → `carryArmed=false` → re-fires `enablePullRequestAutoMerge` and emits a spurious `reviewer_auto_merge_armed` entry + redundant GraphQL mutation each cycle. Compounded: `baseRecord` only persists `lastSeenHeadSha` when truthy (791), so the SHA anchor is lost. The authored stale-approval path already guards on `pr.head?.sha` (429); the reviewer path doesn't. Idempotent on GitHub's side so not catastrophic. _Fix:_ treat missing `headSha` as "not changed" — only compute `headChanged` when `headSha != null`, and carry the armed flag (don't re-fire) when undefined.

- **[engine-correctness] `searchAuthoredPRs` has no per-page error isolation — a failure on page N>1 blanks the whole account's cycle** (`src/github/endpoints.ts:14-24`) — the pagination loop `await`s `request()` per page with no try/catch; a transient 5xx on page 3 rejects the entire search, and the caller returns 0 for ANY error (poll-cycle.ts:185-191), skipping the account that cycle and discarding already-paginated results. Acceptable as fail-safe (a truncated search would mislead transition-detection at poll-cycle.ts:536-551), but a single flaky page shouldn't blank a whole account. _Fix:_ let `RATE_LIMITED`/`AUTH` propagate, but on a transient error after page 1 succeeded, return aggregated-so-far results flagged partial so transition-detection is skipped that cycle (or retry the page once).

- **[architecture] `repoFilter` (display) and `allowRepos` (automation) are two near-identical repo-allowlist concepts with no shared primitive** (`src/core/automations-types.ts:79,119-120`) — both are per-account owner/repo allowlists the popup reasons about together, but case-insensitivity is reimplemented per call site (`allowRepos` lowercased in the filter; `repoFilter` matched in the popup), so the two lists can disagree about what `owner/repo` means (trailing space, case). _Fix:_ extract a tiny `RepoMatcher` primitive (trim+lowercase normalize once; membership test) in core and have both consumers use it — keeps the features distinct while guaranteeing identical normalization.

- **[readability] `RepoFilter` is orphaned dead code with a stale Header-dropdown comment** (`src/popup/components/RepoFilter.tsx:1-114`) — imported by zero non-test files; popup repo filtering is now inline in `PRListView` via `settings.repoFilter`. The header comment still claims it is the live Header dropdown. _Fix:_ delete the component + its test (note: this moots the RepoFilter accessibility findings below), or drop the stale claim and mark it unrendered. **Decide deletion-vs-keep before touching the a11y items on the same file.**

- **[readability] Stale comment: "Stub throws until Part A lands"** (`src/popup/hooks/useAutomationSettings.ts:32`) — Part A `getAutomationSettings` has shipped; the catch comment describes an unimplemented stub, misleading anyone auditing error handling. _Fix:_ reword to the real rationale (transient storage/runtime error; keep defaults so the UI stays usable).

- **[accessibility] No `focus-visible` on PR-row link and ping/tab/repo-filter buttons** (`src/popup/popup.css`; `PRRow.tsx:75`; `PRListView.tsx:245`) — `focus-visible` exists only on `btn`/chevron/checkbox/inputs; the `pr-row` anchor and ping/rerequest/tab pills have none, so keyboard Tab focus is invisible (WCAG 2.4.7); `data-focused` only fires for j/k navigation. _Fix:_ add `focus-visible` outlines to those selectors. (Drop the RepoFilter selector if that component is deleted.)

- **[accessibility] Muted token (~2.6:1) fails AA on skip-badge / status text** (`src/popup/popup.css:8,455-462`) — `term-fg-muted` on `term-bg` is ~2.6:1, below the 4.5:1 AA threshold, and styles `pr-row__skip-badge` status copy ("auto-merge skipped", "merge failed") that low-vision users can't read; `term-fg-dim` is fine. _Fix:_ use `term-fg-dim` or brighter for skip-badge/status text.

- **[accessibility] CT-3 filtered chip has no CSS and reason only in a `title` tooltip** (`src/popup/components/PRRow.tsx:92-100`) — `pr-row__filtered-badge` has no rule in `popup.css`, so it renders as plain text; the skip reason lives only in a `title` attribute (not SR/keyboard reachable) with no `aria-label`. _Fix:_ add a `pr-row__filtered-badge` CSS rule and move the reason into an `aria-label`.

- **[test-gaps] skip-drafts Seam-1 test is tautological** (`tests/background/poll-cycle.ct3-filter.test.ts:163-172`) — a draft PR derives state `draft` in `state-machine.ts:23` BEFORE any rebase check, so `updateBranch` is never called regardless of `skipDraftPRs`; the assertion passes even with `skipDraftPRs:false`. `skipDraftPRs` has zero observable effect at Seam 1, and the test gives false confidence. _Fix:_ delete it, or convert into a real Seam-2 assertion (a `draft`-state PR excluded from the automations candidate list when `skipDraftPRs:true`, included when false).

- **[test-gaps] CT-3 Seam 2 only tests deny-repo — draft and label suppression untested** (`tests/background/poll-cycle.ct3-filter.test.ts:193-224`) — Seam 2 (poll-cycle.ts:651-661) is the ONLY place the filter suppresses non-rebase automations and reads PERSISTED fields `{draft: pr.isDraft, labels: pr.labels}` — a different shape than Seam 1's live `{draft: pr.draft}`. No test covers a persisted-`isDraft:true` draft or an excluded-label PR being dropped at Seam 2, so a regression in how `isDraft` is persisted (poll-cycle.ts:498) would silently break Seam-2 draft suppression. _Fix:_ add Seam-2 tests driven through `runPollCycle` asserting `candidateIds()` excludes a PR for (a) `skipDraftPRs:true` + persisted `isDraft:true`, (b) `excludeLabels` match, (c) `includeLabels` miss.

- **[test-gaps] No test covers the multi-gate interaction matrix (CT-1 backoff × CT-2 CI-red × CT-3 filter)** (`tests/background/poll-cycle.{conflict-backoff,ci-gate,ct3-filter}.test.ts`) — the three rebase gates evaluate in sequence (poll-cycle.ts:311→323→336, `ciRed` gated on `!rebaseSkipped && !rebaseBackedOff`) but their precedence/short-circuit is untested: a CT-3-suppressed PR must NOT fetch the rollup; a CT-3-suppressed-AND-rebase-rejected PR's `rebaseRejectedAtSha` behavior is unpinned (falls through with `finalState='behind'`, possibly dropping the rejected-SHA anchor). _Fix:_ add an interaction-matrix describe block: (a) `denyRepos` + prior rebase-rejected at same SHA → `updateBranch` not called, `getPRStatusRollup` not called, and assert the resulting `rebaseRejectedAtSha` explicitly; (b) skipped/backed-off PR → `getPRStatusRollup` never called.

## Nit

- **[engine-correctness] One `getRepo` failure aborts auto-merge for ALL PRs in the cycle** (`src/background/automations/orchestrator.ts:109-125,344-347`) — Step 1's `Promise.all` over `prs.map` rejects entirely on one non-404 (`getRepo` re-throws non-404 per repos.ts:19-22), skipping `enableAutoMerge` for the whole candidate set; next cycle retries, so no data loss, but one unhealthy repo blocks healthy ones. _Fix:_ `Promise.allSettled` (or per-PR catch returning null on transient errors) to isolate the failure.

- **[engine-correctness] CT-3 filter seam-1 uses live full labels; seam-2 uses persisted name-only labels — `draft` field also differs (`pr.draft` vs `pr.isDraft`)** (`src/background/poll-cycle.ts:302-305 vs 657-660`) — both default fail-open and normally agree, but a `getPR` that omits `draft` lets the two seams reach different suppression verdicts in the same cycle. The label name-only design is documented; the draft divergence isn't. _Fix:_ document the seam-2-reads-persisted choice for `draft` (as for labels), or confirm `isDraft` can't go stale relative to the persisted labels it's filtered with.

- **[architecture] `PRRecordPhaseTwo` is a ~100-line grab-bag of ~20 independently-optional fields spanning 6+ features** (`src/core/automations-types.ts:179-285`) — every field optional, so the type expresses no invariant (e.g. `reviewerAutoMergeArmed` set with `myReviewState` undefined). Works because each automation reads only its slice; design-debt signal. _Fix (defer if churn outweighs gain):_ group per-feature fields into nested optional sub-objects so an absent feature is one absent key.

- **[security] `console.warn` logs the raw error from a `/user` fetch made with the legacy token** (`src/background/auth-device-flow-runner.ts:131`) — `fetch()` rejections don't embed request headers, so the token is NOT exposed (clean per the fetch spec); flagged only as the single log site adjacent to a bearer token. _Fix (optional):_ log `e.message` or a fixed string to make the no-leak property robust against future refactors.

- **[security] `optional_host_permissions: ["https://*/*"]` is broad (documented, narrowed at request time)** (`manifest.json:13-15`) — narrowed to `https://${host}/*` in `SettingsView.requestHostPermission` and fail-closed by `assertGithubOrigin`, so a granted-but-unused broad grant can't exfiltrate the token; pre-existing, not a CT regression. _Fix:_ none required; optionally request the GHES wildcard only when `enterpriseHost` is configured.

- **[readability] Two duplication nits: default-expansion rule and a repeated comment** (`src/popup/views/PRListView.tsx:153,287`; `App.tsx:23-30`) — `defaultExpanded` rule duplicated at PRListView:153 (flatVisiblePRs) and :287 (render) must stay in lockstep; App.tsx:23-25 and 27-30 explain the same viewport-pin fact twice. _Fix:_ extract one `defaultExpandedFor` helper; keep one App.tsx comment.

- **[readability] Ungrammatical settings label** (`src/popup/components/AutomationsSettings.tsx:519`) — reads "Auto-enable auto-merge after I approval if last required gate". _Fix:_ "Auto-enable auto-merge after I approve, if I am the last required reviewer."

- **[test-gaps] `registerNotificationClickListener` (the MV3-eviction wake path) is uncovered** (`src/background/notifications.ts:221-222`) — the click HANDLER is well tested but the listener-registration shim is not; a regression dropping the `addListener` call leaves clicks dead in production with all handler tests still green. _Fix:_ one test stubbing `chrome.notifications.onClicked.addListener`, assert registration + that the captured callback routes to `handleNotificationClick`; plus a `typeof chrome === 'undefined'`/missing-`onClicked` early-return guard.

- **[test-gaps] Cross-account isolation test never exercises any CT gate per-account** (`tests/background/poll-cycle.cross-account.test.ts`) — proves accountId threading solidly, but every PR is `clean` with inert settings, so it never verifies a CT-1/2/3 decision for account A doesn't leak into B. _Fix (optional):_ give account A a behind PR with `denyRepos:[A-repo]` and B a behind PR in an allowed repo, assert `updateBranch` fires only for B.

- **[accessibility] `role=menu` wrapping checkbox labels is the wrong ARIA pattern** (`src/popup/components/RepoFilter.tsx:75-92`) — panel is `role=menu` but children are label+checkbox rows, not menuitems; trigger uses `aria-haspopup=menu`, inconsistent for AT. _Fix:_ `role=group`+`aria-label`, or `role=menuitemcheckbox`+`aria-checked`. **Moot if RepoFilter is deleted (see should-fix).**

- **[accessibility] Three SR nits: no poll live region, missing `h1`, `aria-hidden` PR number** (`Header.tsx:49`; `SettingsView.tsx:99`; `PRRow.tsx:101`) — no `aria-live`/`role=status` so a completed poll re-render is silent; page titles are spans not `h1`; `pr-row__num` is `aria-hidden` so similar PRs are indistinguishable. _Fix:_ add a hidden `role=status aria-live=polite`; promote title to `h1`; drop the `aria-hidden` or add the number to the row `aria-label`.

## Test-gap summary

The CT-wave's risk concentrates where tests are thinnest — the **automations candidate filter (Seam 2)** and the **multi-gate ordering**, both of which the two must-fixes and CT-6 touch.

1. **Tautological / missing Seam-2 coverage (highest risk).** The skip-drafts Seam-1 test proves nothing (a draft PR is unreachable for rebase by construction), and Seam 2 — the only place non-rebase automations are suppressed, reading a *different persisted field shape* (`pr.isDraft`/name-only labels) than Seam 1 — has only deny-repo coverage. A regression in `isDraft` persistence (poll-cycle.ts:498) would break draft suppression invisibly. Convert the Seam-1 test to a real Seam-2 assertion and add draft/excludeLabels/includeLabels cases driven through `runPollCycle`.
2. **Gate-interaction matrix.** Each rebase gate (CT-1 backoff / CT-2 CI-red / CT-3 filter) is tested in isolation; their precedence and the `rebaseRejectedAtSha` behavior under a simultaneous CT-3 suppress are unpinned. Add an interaction-matrix block.
3. **Settings roundtrip on the v2 path.** No test covers `enableIgnoredRepos=false` surviving save→read with an active account (the must-fix bug) or surviving v1→v2 migration + a subsequent save. Add both.
4. **Cross-account gate isolation + notify isolation.** The cross-account test threads accountId but never exercises a CT decision or a notification per-account. Add the notify-throttle isolation test (required for CT-5) and optionally a per-account filter-isolation case.
5. **MV3 wake-path registration.** `registerNotificationClickListener` is uncovered; a dropped `addListener` leaves clicks dead in prod with green handler tests. Add a one-line registration test + a missing-API guard test.
